# 1. FixGo 프로젝트 개요

## 1.1 서비스 소개

FixGo는 사자전자의 스마트폰·노트북 A/S를 접수부터 제품 반환까지 한 흐름으로 다루는 **내부 A/S 업무 통합관리 시스템**입니다. 고객용 회원가입은 없으며, 관리자가 발급한 직원 계정으로만 업무 화면에
들어갑니다. 고객은 접수 건마다 발급된 전용 링크에서 진행 상태, 견적, 결제, 배송을 확인합니다.

- 관리자(`ADMIN`): 직원 계정·역할, 지원 품목, 부품·공임비, 통계, 기사 배정 이력과 A/S 상태 변경 이력
- 접수 담당자(`RECEPTIONIST`): A/S 접수·배정, 고객·제품 조회, 결제·배송, 고객 알림
- 수리 기사(`TECHNICIAN`): 본인에게 배정된 점검·수리, 수리 프리셋, 견적과 수리비 산정

핵심 흐름은 접수 → 담당 기사 배정 → 점검·견적 → 고객 승인 → 수리 → 결제 → 택배 반환 또는 방문 수령입니다. 보증 판정, 서류(접수증·견적서·수리 내역서·영수증), 운영 통계, 영수증 이미지 분석으로
수기 장부와 엑셀에 흩어진 업무를 한곳으로 모읍니다.

## 1.2 핵심 기술 스택

- 백엔드: Java 25, Spring Boot 4.1.x, Gradle, Spring Data JPA, Spring Security, JJWT 0.13, springdoc OpenAPI, Spring AI,
  Apache POI, Spring Mail
- 프론트엔드: React 19.x, TypeScript 6.x, Vite 8.x, Tailwind CSS 4.x, Zustand 5.x, React Router 8.x
- 데이터베이스: MySQL 9.x (운영), H2 Database (테스트)
- 인프라 및 DevOps: AWS EC2, Docker, Docker Compose, Nginx, MySQL, AWS S3(직원 프로필), Netlify, Cloudflare, GitHub Actions CI/CD
- 외부 연동: 토스페이먼츠(카드·계좌이체·가상계좌), 카카오 주소 검색, 택배 배송 조회, SMS·이메일 알림, AI 영수증 분석

로컬 개발에서는 Vite가 `/api`를 Spring Boot `8080`으로 프록시합니다. API prefix는 `/api/v1`입니다.

## 3.1 프로젝트 기획서 (Project Proposal)

### 3.1.1 정의

프로젝트의 출발점으로서 FixGo의 목적, 배경, 핵심 업무 가치(접수·점검·견적·수리·결제·반환의 일원화), 팀원별 도메인 역할 분담을 정하는 기본 기획 문서.

### 3.1.2 작성 필요성 및 목적

- 프로젝트 방향성 통일: 팀원 간 서비스 목표와 업무 모델(직원 접수, 견적 승인 후 수리, 결제 후 배송 또는 방문 수령)에 대한 이해를 맞추고 기획 혼선을 막는다
- 개발 범위 명확화: 구현할 서비스 범위와 프론트엔드·백엔드 연동 목표를 정한다

### 3.1.3 필수 포함 항목

- 프로젝트명 및 한 줄 서비스 소개
- 프로젝트 기획 배경 및 목적

- 주요 기능 요구사항 요약
- 팀 구성 및 도메인별 역할 분담표

## 3.2 요구사항 기능 명세서 (PRD)

### 3.2.1 정의

시스템이 제공해야 하는 세부 기능을 도출하고, 기능별 구현 조건, 대상 역할(RBAC), 우선순위를 목록으로 관리하는 문서.

### 3.2.2 작성 필요성 및 목적

- 개발 스코프 제어: 반드시 구현할 기능(1순위)과 권장·선택 기능(2, 3순위)을 구분한다
- 개발 구현 기준 제공: 기능별 입력, 처리, 출력과 예외 규칙을 구체화한다
- 인증·결제·상태 전이 명시: JWT 인증, 토스페이먼츠 승인·웹훅, A/S 상태 전이, 역할별 접근 제어를 사전에 정한다

### 3.2.3 필수 포함 항목 및 작성 방법

- 요구사항 식별 ID: `REQ-AUTH-01`, `REQ-MASTER-01`, `REQ-INTAKE-01`, `REQ-REPAIR-01`, `REQ-PAY-01`, `REQ-PORTAL-01`,
  `REQ-FULFILL-01`, `REQ-SMS-01`, `REQ-STAT-01`처럼 도메인별 코드를 부여한다
- 구분: 인증·직원, 고객·제품·부품, A/S 접수·배정, 수리·상태, 결제, 고객 포탈, 배송, 알림, 통계
- 기능명 및 대상 역할: `ADMIN`, `RECEPTIONIST`, `TECHNICIAN` 를 구분한다. 고객 포탈은 계정 없이 링크 토큰으로 접근한다
- 우선순위: 1순위(필수 구현), 2순위(주요 권장), 3순위(추가 선택)
- 상세 내용: 동작 조건과 입력 검증 규칙을 적는다
- RBAC 권한 매트릭스: 도메인·기능별 역할 허용 여부(O/X)

- 요구사항 기능 명세서: [A/S 관리 시스템 요구사항 명세서](01_planning/02_prd.md)

## 3.3 코드 컨벤션 정의서 (Code Convention Document)

### 3.3.1 정의

팀원 전체가 한 사람이 작성한 것처럼 보이도록 코딩 스타일, 네이밍, 디렉터리, 백엔드 레이어 원칙(DTO와 Entity 분리, 생성자 주입, 트랜잭션 경계), Git 협업 규약을 적는 개발 표준 문서.

### 3.3.2 작성 필요성 및 목적

- 코드 가독성: 서식과 이름을 맞춰 다른 팀원의 코드를 읽는 시간을 줄인다
- 리뷰 집중: 포맷 논쟁 대신 업무 규칙과 설계를 본다
- 런타임 결함 예방: DTO와 Entity 분리, 생성자 주입, `@Transactional(readOnly)`로 순환 참조·지연 로딩·불필요한 쓰기 트랜잭션을 줄인다

### 3.3.3 필수 포함 항목

- 백엔드 서식: 들여쓰기 공백 4칸, 최대 줄 너비 120자, K&R 중괄호, 단문 제어문도 중괄호, 와일드카드 import 금지
- 식별자: 패키지 루트 `net.likelion.bebc25.fixgo`, 역할 접미사(Controller, Service, Repository, Dto, Entity), 메서드 동사, DB 컬럼 스네이크 케이스
- 레이어: 계층별 책임, DTO와 Entity 분리, 생성자 주입, 선언적 트랜잭션, 전역 예외 응답
- 프론트엔드: 함수 컴포넌트, TypeScript strict, 들여쓰기 공백 2칸, 경로 별칭 `@` → `src`
- Git: Conventional Commits, 브랜치 `main`, `develop`, `feature/*`, `fix/*`, PR 점검 목록

- 코드 컨벤션 정의서: [AS업무 통합관리시스템 - FixGo 코드 컨벤션 정의서](01_planning/03_convention.md)

## 3.4 시스템 아키텍처 구성도 (System Architecture Diagram)

### 3.4.1 정의

React SPA부터 Spring Boot REST API, MySQL, AWS·Netlify 배포, 토스페이먼츠, 주소 검색, 배송 조회, SMS·이메일, AI 영수증 분석까지의 구조와 데이터 흐름을 그린 구성도.

### 3.4.2 작성 필요성 및 목적

- 클라이언트와 서버 분리: React와 Spring Boot 사이 비동기 REST, JWT 전달 방식을 명확히 한다
- 배포 구조: Netlify·Cloudflare의 정적 사이트, EC2의 Nginx·Docker Compose·Spring Boot, S3 프로필 저장을 한눈에 본다
- 데이터 흐름: 로그인, 견적 승인, 결제 승인·웹훅, 배송 상태, 고객 알림, 영수증 분석을 적는다

### 3.4.3 필수 포함 항목

- 프론트엔드: Netlify에 Vite 빌드 결과 배포, Cloudflare DNS·HTTPS, SPA fallback으로 `index.html` 반환
- 백엔드: AWS EC2, Nginx(80/443), Docker Compose, Spring Boot REST API(8080)
- 데이터베이스: MySQL 3306, 볼륨으로 데이터 유지
- 외부 연동 및 스토리지: S3 프로필, 토스페이먼츠, 카카오 주소 검색, 택배 조회, SMS·이메일, AI API
- CI/CD: GitHub Actions로 테스트·이미지 빌드 후 EC2에서 `docker compose`로 기동

- 시스템 아키텍처 설계서: [시스템 아키텍처 설계서 (FixGo)](02_design/01_architecture.md)
- 인프라·배포 구성: [시스템 아키텍처 구성](02_design/01_architecture.md)

## 3.5 데이터베이스 ERD (Entity Relationship Diagram)

### 3.5.1 정의

테이블 구조, 컬럼 타입, PK/FK 제약, 테이블 간 관계(1:1, 1:N, N:M)를 정한 개체 관계도.

### 3.5.2 작성 필요성 및 목적

- 데이터 무결성: 접수번호·직원 이메일 유일성, 접수 1건당 수리·청구·배송 관계, 결제 시도·웹훅 중복 방지
- JPA 연관관계: 다대일·일대다를 미리 정하고, 컬렉션을 한 번에 여러 개 페치 조인하지 않는 조회 구조를 둔다

### 3.5.3 필수 포함 항목

- 테이블·컬럼 명세: PK, FK, Not Null, Unique, Default
- 핵심 테이블: `member`, `refresh_token`, `customer`, `product_model`, `product`, `as_reception`, `as_attachment`,
  `as_status_history`, `symptom_preset`, `repair_preset`, `repair`, `repair_work`, `repair_photo`, `part`,
  `part_stock_history`, `payment_bill`, `payment_attempt`, `virtual_account`, `shipment`, `shipment_event`,
  `customer_portal_link`, `notification_log`, `receipt_analysis`, `outbox_event`
- 작성 방식: 마크다운 안 Mermaid `erDiagram`

### 3.5.4 Mermaid ERD 주요 문법

- Mermaid ERD 문법: [https://docs.mermaidviewer.com/diagrams/er.html](https://docs.mermaidviewer.com/diagrams/er.html)
- 관계 기호:
    - 1:1 (양쪽 필수): `||--||`
    - 1:1 (한쪽 필수, 반대쪽 0 또는 1): `||--o|`
    - 1:N (한쪽 필수, 반대쪽 1개 이상): `||--|{`
    - 1:N (한쪽 필수, 반대쪽 0개 이상): `||--o{`
    - N:M (양쪽 1개 이상): `}|--|{`
    - N:M (한쪽 1개 이상, 반대쪽 0개 이상): `}|--o{`
- 기호 의미:
    - `||`: 정확히 1개
    - `|{`: 1개 이상
    - `o{`: 0개 이상
    - `o|`: 0개 또는 1개
- 구성 요소:
    - `|`: 최소 1개 (필수)
    - `o`: 0개일 수 있음 (선택)
    - `}` 또는 `{`: 다수

- 데이터베이스 ERD: [02_ERD](02_design/02_erd.md)

## 3.6 화면 설계서 (UI Wireframe)

### 3.6.1 정의

### 3.6.2 작성 필요성 및 목적

## 3.7 REST API 명세서 및 규격서 (API Specification)

### 3.7.1 정의

프론트엔드와 백엔드가 JSON으로 통신하기 위해 맞춘 URI, HTTP 메서드, 요청·응답 DTO 문서.

### 3.7.2 작성 필요성 및 목적

- 병렬 개발: API가 끝나기 전에 합의된 JSON으로 화면을 먼저 만든다
- 연동 전환: 더미 호출을 `/api/v1` 실제 호출로 바꾼다
- 오류 형식 통일: 실패 시 응답 바디의 `message`를 사용자에게 보여 준다

### 3.7.3 필수 포함 항목

- 공통 응답: 단건, 목록·페이지, 오류 바디
- 인증·직원 API: 로그인, 토큰 갱신, 로그아웃, 내 정보, 비밀번호 변경, 직원 등록·조회·수정·비활성화, 역할 부여
- 고객·제품 API: 고객 등록·검색·수정, 엑셀 양식·업로드, 제품 모델, 시리얼 조회, 부품
- A/S API: 접수 등록·목록·상세·수정, 기사 배정, 점검·수리, 프리셋, 보증, 견적, 상태 전이, 서류
- 결제 API: 청구, 결제 시도, 승인 검증, 웹훅, 가상계좌, 현장 수납, 환불
- 고객 포탈 API: 링크 검증, 진행·견적·수리·결제 조회, 견적 승인·거부
- 배송 API: 운송장 등록, 상태 조회, 배송 완료, 방문 수령
- 알림 API: 발송, 이력, 프리셋, 발송 결과 웹훅
- 통계 API: 운영 현황, 기사·모델·고장 증상, 수리비, 미입금, 배송, 장기 미처리

- REST API 명세서: [REST API 명세서 및 규격서 (FixGo MS)](02_design/04_api_specification.md)

## 3.8 트러블슈팅 및 기술 문제 해결 기록 (Troubleshooting Log)

### 3.8.1 정의

개발과 배포에서 만난 런타임 오류, 쿼리, 인증·권한, 결제·배송 웹훅, 알림 실패, 배포 파이프라인 문제의 원인, 해결, 시사점을 남기는 문서.

### 3.8.2 작성 필요성 및 목적

- 같은 문제의 반복을 줄인다. 해결 기록을 팀원이 다시 볼 수 있게 둔다
- JWT·RBAC, A/S 상태 전이, 토스페이먼츠 금액 검증과 웹훅 중복, 배송 이벤트, 고객 포탈 토큰, JPA 조회, Docker·GitHub Actions 배포 경험을 문서로 남긴다

### 3.8.3 필수 포함 항목 및 작성 템플릿

- 작성자 식별자: `TS-[작성자영문]-[순번]`
  (예: `TS-HYERAN-01`, `TS-BYEONGHO-01`, `TS-NAMGYU-01`, `TS-SUHWAN-01`, `TS-WONIL-01`, `TS-JIWON-01`,
  `TS-SEUNGHYEOK-01`)
- 복사용 템플릿:

````markdown
## TS-[작성자영문]-[순번]: [발생한 문제 및 에러 제목]

### 1) 발생 현상 및 에러

- 런타임 현상과 에러 로그 또는 화면에서 보인 메시지를 적는다.

### 2) 원인 분석

- 문제가 난 지점과 코드 흐름을 적는다.

### 3) 해결 방법

- 바꾼 내용과 핵심 코드를 적는다.

```java
// 해결 핵심 소스 코드
```

### 4) 시사점 및 배운 점

- 같은 문제가 다시 나지 않도록 남길 점을 적는다.
````
