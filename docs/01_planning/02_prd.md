# B2B A/S 관리 시스템 요구사항 명세서

본 시스템은 **단일 A/S 업체·단일 지점**에서 내부 직원이 사용하는 업무 관리 시스템이다. 개인·기업 고객을 관리하지만 고객용 계정·포털은 제공하지 않는다. 고객의 전화·이메일·방문 요청을 직원이 대리
접수한다.

# 3. 비기능 요구사항 및 CI/CD 자동화

### 1) 데이터 정합성 및 보안 요구사항

- **인증·인가:** Spring Security와 JWT를 사용하며, `ADMIN`, `RECEPTIONIST`, `TECHNICIAN` 역할을 API에서 검증한다. 고객은 로그인하지 않는다.
- **비밀번호 보호:** BCrypt 등 안전한 단방향 해시를 사용한다. 비활성 직원의 로그인과 보호 API 접근을 차단한다.
- **입력값 검증:** `@Valid`, `@NotNull`, `@Size` 등 Bean Validation과 `@RestControllerAdvice`로 표준 오류 응답을 제공한다.
- **업무 상태 정합성:** `AS_REQUEST.status` 변경과 `AS_STATUS_HISTORY` 기록은 같은 DB 트랜잭션으로 처리한다. 접수 → 수리 중 → 입금대기 → 배송대기 → 완료 등 허용된
  전이만 수행한다.
- **수리비 정합성:** `REPAIR_ITEM`의 실제 적용 단가·수량을 보존하고, 확정 후 임의 수정과 음수 금액을 제한한다.
- **결제 웹훅 멱등성:** PG 이벤트를 검증·기록하고 중복 웹훅 및 수동 입금 확인과의 경합에도 결제 완료가 한 번만 반영되도록 한다. 외부 PG API 호출과 로컬 DB 커밋은 하나의 DB 트랜잭션으로
  원자화할 수 없으므로 상태·재조회·재시도 정책으로 정합성을 확보한다.
- **배송 이벤트 멱등성:** 모의 배송 웹훅의 중복 수신이 상태 변경을 중복 실행하지 않도록 한다.
- **개인정보 보호:** 고객 연락처·주소와 웹훅 원문 등 민감 정보는 최소 수집하고 로그에 마스킹한다.
- **선택 기능:** SMS Outbox는 업무 트랜잭션에 발송 요청을 함께 저장하고 별도 처리기로 재시도한다. AI 분석에는 고객 개인정보를 전달하지 않는다.

### 2) 성능 및 데이터 처리 요구사항

- **조회 성능:** 고객 검색, A/S 상태·담당 기사·접수일 필터에 적합한 인덱스를 설계하고 목록은 페이지네이션을 적용한다.
- **JPA 조회 최적화:** 연관 엔티티 조회 시 N+1 문제를 확인하고 필요한 경우 Fetch Join, DTO 조회 또는 배치 조회를 선택한다.
- **통계 쿼리:** 운영 대시보드의 집계 SQL은 MyBatis로 작성하고 실행계획을 확인한다.
- **엑셀 업로드:** Apache POI를 활용해 고객 데이터의 필수값·형식·중복 후보를 검증하고 행별 오류를 반환한다. 4주 범위에서는 Spring Batch 도입을 필수로 하지 않는다.
- **동시성 테스트:** 동일 A/S 건의 상태 변경, 중복 입금 웹훅, 수동·자동 입금 확인 경합을 통합 테스트한다.

### 3) CI/CD 배포 자동화 파이프라인

- **지속적 통합(CI Pipeline):**
    - `develop` 및 `main` 브랜치의 PR·Push 시 빌드와 테스트를 실행한다.
    - JDK·Gradle 캐시를 적용하고 Spring Boot 단위·통합 테스트(JUnit 5)를 수행한다.
    - 테스트 실패 시 병합 또는 배포를 차단하고 PR에서 결과를 확인한다.
    - React 프런트엔드도 별도 빌드·정적 검사를 수행한다.
- **지속적 배포(CD Pipeline):**
    - CI 통과 후 백엔드 JAR과 프런트엔드 정적 파일을 빌드한다.
    - Docker 이미지를 생성하고 AWS EC2 환경에 배포한다.
    - Docker Compose로 애플리케이션을 실행하고 환경 변수·비밀값을 분리한다.
    - 헬스체크로 기동 상태를 확인하고 배포 실패 시 복구 절차를 마련한다.
    - **단일 EC2·단일 애플리케이션 컨테이너 구성은 무중단 롤링 배포를 보장하지 않는다.** 무중단 배포가 필요하면 별도 블루·그린 구성 등을 설계한다.
- **도구 선택:** GitHub Actions을 사용한다.

### 4) 테스트 및 운영 요구사항

- **API 명세:** Swagger/OpenAPI에 인증 방식, 역할 권한, 요청·응답·오류 코드를 문서화한다.
- **핵심 통합 시나리오:** 직원 로그인 → 고객·제품 등록 → A/S 접수 → 기사 배정 → 수리비 확정 → 가상계좌 발급 → 입금 웹훅 → 배송·방문 수령 → 완료.
- **예외 시나리오:** 접수 반려·취소, 비활성 계정, 권한 없는 수리 접근, 중복 웹훅, 입금액 불일치, 외부 SMS 장애, 잘못된 상태 전이.
- **구현 우선순위:** 결제·배송·SMS 기본 흐름과 정합성 테스트를 우선 완료하고, Outbox·AI 분석·감사 로그 고도화는 2순위로 진행한다.
