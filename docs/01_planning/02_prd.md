# 1. 기능 요구사항 명세표

## 1) 회원 및 계정 관리

| 요구사항 ID | 구분 | 기능명 | 담당자 | 우선순위 | 상세 내용 |
| --- | --- | --- | --- | --- | --- |
| REQ-USER-01 | 인증 | 로그인 | 1번 | 1순위 | 등록된 사용자가 아이디와 비밀번호로 로그인하며, 계정 상태와 권한을 확인한 후 역할별 화면으로 이동 |
| REQ-USER-02 | 인증 | 로그아웃 | 1번 | 1순위 | 사용자가 로그아웃하면 인증 상태를 해제하고 로그인 화면으로 이동 |

| REQ-USER-04 | 회원 | 내 정보 조회 및 수정 | 1번 | 1순위 | 사용자가 본인의 이름, 연락처, 소속 조직 및 역할을 조회하고 수정 가능한 개인정보를 변경 |

| REQ-USER-06 | 본사 계정 | 최고관리자 계정 관리 | 1번 | 1순위 | 시스템에 사전 등록된 최고관리자 계정으로 로그인하며, 최고관리자 계정은 일반 사용자 관리 화면에서 생성하지 않음 |
| REQ-USER-07 | 센터 계정 | 센터 관리자 계정 관리 | 1번 | 1순위 | 본사 최고관리자가 센터 관리자를 등록하고 소속 A/S 센터를 지정·변경 |
| REQ-USER-08 | 센터 계정 | 센터 직원 계정 관리 | 1번 | 1순위 | 센터 관리자가 소속 접수 담당자와 수리 기사 계정을 등록·조회·수정·비활성화 |
| REQ-USER-09 | 센터 계정 | 센터 직원 업무 권한 설정 | 1번 | 1순위 | 센터 관리자가 직원에게 접수 담당자 또는 수리 기사 권한을 부여하며, 필요하면 두 권한을 함께 부여 |
| REQ-USER-10 | 고객사 계정 | 고객사 관리자 계정 관리 | 1번 | 1순위 | 본사 관리자가 등록된 고객사에 관리자 계정을 발급하고 계정 상태를 관리 |
| REQ-USER-11 | 고객사 계정 | 고객사 직원 계정 관리 | 1번 | 1순위 | 고객사 관리자가 소속 직원의 계정을 등록·조회·수정·비활성화 |
| REQ-USER-12 | 계정 | 계정 비활성화 | 1번 | 1순위 | 비활성화된 계정의 로그인을 차단하되 기존 A/S 접수·수리·결제 이력은 유지 |
| REQ-USER-13 | 계정 | 비밀번호 초기화 | 1번 | 2순위 | 권한 있는 관리자가 하위 사용자 계정의 비밀번호를 안전한 절차에 따라 초기화 |
| REQ-USER-14 | 계정 | 계정 목록 검색 | 1번 | 2순위 | 관리 권한 범위 내에서 사용자 이름, 역할, 소속 조직, 계정 상태로 계정 검색 및 조회 |

| REQ-CUST-06 | 계약 | 고객사 계약 등록 | 2번 | 1순위 | 본사 최고관리자가 고객사의 계약 시작일, 종료일, 계약 상태 및 계약 내용을 등록 |
| REQ-CUST-07 | 계약 | 고객사 계약 조회 | 2번 | 1순위 | 고객사별 계약 기간, 계약 상태 및 주요 계약 정보를 조회 |
| REQ-CUST-08 | 계약 | 고객사 계약 수정·종료 | 2번 | 1순위 | 본사 최고관리자가 계약 기간과 상태를 변경하고 계약 종료 시 종료 정보를 기록 |
| REQ-CUST-09 | 계약 | 계약 만료 예정 조회 | 2번 | 2순위 | 계약 종료일을 기준으로 만료 예정 고객사를 조회하고 목록에서 구분 |
| REQ-CUST-10 | 담당자 | 고객사 업무 담당자 관리 | 2번 | 1순위 | 고객사의 A/S 업무 담당자 이름, 부서, 연락처 및 이메일을 등록·조회·수정 |
| REQ-CUST-11 | 담당자 | 대표 담당자 지정 | 2번 | 2순위 | 고객사별 대표 A/S 담당자를 지정하여 업무 연락 및 안내에 활용 |
| REQ-CUST-12 | 고객사 | 고객사 정보 조회 | 2번 | 1순위 | 고객사 관리자와 직원이 소속 고객사의 기본 정보 및 계약 상태를 조회 |

## 3) A/S 센터 관리

| 요구사항 ID | 구분 | 기능명 | 담당자 | 우선순위 | 상세 내용 |
| --- | --- | --- | --- | --- | --- |
| REQ-CENTER-01 | 센터 | A/S 센터 등록 | 1번 | 1순위 | 본사 최고관리자가 센터명, 센터 코드, 주소, 대표 연락처, 운영 상태 등을 입력하여 A/S 센터 등록 |

| REQ-CENTER-03 | 센터 | A/S 센터 상세 조회 | 1번 | 1순위 | 센터 기본 정보, 소속 직원, 수리 가능 제품 모델 및 운영 상태 조회 |
| REQ-CENTER-04 | 센터 | A/S 센터 정보 수정 | 1번 | 1순위 | 본사 최고관리자가 센터의 주소, 연락처, 센터명 등 기본 정보 수정 |
| REQ-CENTER-05 | 센터 | A/S 센터 운영 상태 관리 | 1번 | 1순위 | 본사 최고관리자가 센터를 운영 중 또는 운영 중지 상태로 변경하며, 운영 중지된 센터는 신규 A/S 접수 대상에서 제외하고 기존 처리 이력은 유지 |
| REQ-CENTER-06 | 직원 | 센터 소속 직원 조회 | 1번 | 1순위 | 본사 최고관리자와 해당 센터 관리자가 소속 직원의 이름, 역할, 계정 상태 등을 조회 |
| REQ-CENTER-07 | 직원 | 센터 소속 직원 변경 | 1번 | 2순위 | 본사 최고관리자가 직원의 소속 센터를 변경하며, 기존 A/S 처리 이력은 유지 |
| REQ-CENTER-08 | 수리 가능 제품 | 센터별 수리 가능 제품 등록 | 3번 | 1순위 | 본사 최고관리자가 제조기업의 제품 모델 목록에서 해당 센터가 수리할 수 있는 모델을 선택하여 등록 |
| REQ-CENTER-09 | 수리 가능 제품 | 센터별 수리 가능 제품 조회 | 3번 | 1순위 | 본사 최고관리자와 센터 관리자가 해당 센터에서 수리 가능한 제품 모델 목록 조회 |
| REQ-CENTER-10 | 수리 가능 제품 | 센터별 수리 가능 제품 변경 | 3번 | 1순위 | 본사 최고관리자가 센터의 수리 가능 제품 모델을 추가하거나 해제하며, 기존 A/S 처리 이력은 유지 |
| REQ-CENTER-11 | 수리 가능 제품 | 제품별 수리 가능 센터 조회 | 3번 | 1순위 | 특정 제품 모델을 수리할 수 있는 운영 중인 센터 목록을 조회하여 A/S 접수 시 센터 선택에 활용 |
| REQ-CENTER-12 | 센터 | 센터별 A/S 업무 현황 조회 | 1번 | 2순위 | 본사 최고관리자와 센터 관리자가 권한 범위 내에서 센터별 접수 건수, 진행 중 건수, 완료 건수 조회 |

# 3. 비기능 요구사항 및 CI/CD 자동화

### 1) 데이터 정합성 및 보안 요구사항
- 결제 검증 원자성: 결제 사전 검증(결제 대기 레코드 생성)과 사후 검증(PG사 실결제 금액 대조 및 수강권 발급)은 단일 트랜잭션(@Transactional) 내에서 처리되어 데이터 불일치 차단.
- 인증/인가 무상태성: Spring Security와 JJWT를 활용하여 서버 세션 의존성을 제거하고, 토큰 탈취 방지를 위한 RTR(Refresh Token Rotation) 체계 필수 적용.
- 입력값 검증: 컨트롤러 계층 진입 시 Spring Boot Validation(@Valid, @NotNull, @Size 등)을 통한 사전 유효성 검증 및 전역 예외 처리기(@RestControllerAdvice) 표준 응답 반환.

### 2) 성능 및 대용량 데이터 처리 요구사항
- 쿼리 최적화: 강좌 상세 및 커리큘럼 조회 시 JPA Fetch Join을 적용하여 N+1 문제 원천 차단, 복합 검색 쿼리는 QueryDSL 기반 인덱스 친화적 동적 쿼리 구성.
- 대용량 배치 프로세싱: Spring Batch 기반 대용량 일괄(Chunk) 프로세싱을 도입하여 수만 건의 수강 만료 및 정산 데이터를 페이징 단위(예: 500건)로 안전하게 처리.

### 3) GitHub Actions 기반 CI/CD 배포 자동화 파이프라인
- 지속적 통합 (CI Pipeline):
  - main 및 develop 브랜치 대상 Pull Request(PR) 및 Push 이벤트 감지.
  - JDK 및 Gradle 캐싱 환경 설정.
  - Gradle 컴파일 및 단위/통합 테스트(JUnit5) 자동 실행.
  - 테스트 실패 시 배포 파이프라인 즉시 중단 및 GitHub PR 피드백 표시.
- 지속적 배포 (CD Pipeline):
  - CI 파이프라인 통과 후 Spring Boot 애플리케이션 JAR 빌드.
  - Docker 멀티 스테이지 빌드를 통한 경량화된 컨테이너 이미지 자동 생성.
  - AWS EC2 인스턴스로 SSH 원격 접속 및 Docker Compose 기반 신규 컨테이너 무중단 롤링 배포 수행.
  - Nginx 헬스체크 검증 후 배포 완료 알림 전송.
